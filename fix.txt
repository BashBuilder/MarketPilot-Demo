# Frontend follow-ups after backend create-campaign investigation

## What was broken

`POST /api/v1/campaigns` created the campaign and run, but the backend launcher
only recorded the run id (`RecordingRunLauncher`). The workflow never started,
so `GET /runs/{run_id}/stream` stayed open with no events. The run stayed
`pending` with zero checkpoints.

Backend fix applied (no frontend change needed):

- The production launcher now starts the LangGraph workflow in a background task.
- A real DeepSeek structured-output client is wired in.
- Failures mark the run and campaign `failed` and emit a terminal `error` event.
- Campaign status now follows the run: `running` -> `awaiting_approval` ->
  `completed`, or `failed`.

## Frontend mismatches / gaps to adjust

### 1. SSE reconnect does not use `Last-Event-ID`

File: `frontend/src/lib/sse/useRunStream.ts` (around lines 46-53 and 129-139)

The contract says a client resumes with `Last-Event-ID`. The frontend instead
closes the connection in `onerror` and reopens it with a query parameter
`?last_event_id=...`. The backend only reads the `Last-Event-ID` header, so the
query parameter is ignored.

Recommended fix: on an unexpected drop, do not call `stream.close()` and do not
schedule a manual reconnect. Leave the `EventSource` open so the browser
reconnects natively and sends `Last-Event-ID` automatically. Keep the explicit
`close()` only for terminal events (`awaiting_approval`, `completed`, and
non-recoverable `error`), as already implemented. Keep event-id deduplication.

If a manual reconnect must stay, the backend contract would need to accept
`last_event_id` as a query parameter, and both `agent.md` files would have to be
updated in the same commit.

### 2. No idle / stale-stream state

File: `frontend/src/app/campaigns/[id]/run/[runId]/live-run-view.tsx`

The view shows “Waiting for the run to start” indefinitely while the stream is
open but silent. The requirement is to show loading, empty and error states
honestly. Add a bounded “no progress yet” state after an open stream receives no
events for a configurable period, with a reload action. Do not treat a slow LLM
call as a failure immediately; a generous threshold (for example 60-90s) is
appropriate.

### 3. Package schema rejects partially produced versions

Files: `frontend/src/lib/schemas/package.ts`, `frontend/src/app/campaigns/[id]/versions/[n]/page.tsx`

If a node exhausts its retries and escalates to the human gate before all seven
sections exist, the backend snapshots the state with `null` for the missing
sections. `campaignPackage` requires every section to be present, so the version
page turns into a generic error instead of showing what was produced.

Decide with the backend owner whether the contract should:

- allow nullable package sections and render an explicit “not produced” state
  for each missing section, or
- guarantee that only complete packages are versioned.

Do not silently drop the fields. If the contract changes, update section 2 of
both `backend/agent.md` and `frontend/agent.md` in the same commit.

### 4. `/v1/models` 404 in the backend log is not a frontend API call

No frontend source references `/v1/models`. It is not part of the API contract,
so no frontend change is needed for it.

## Verification expected after the frontend changes

- Create a campaign against the real backend and confirm the live view receives
  `agent_started` / `agent_handoff` events instead of staying idle.
- Drop the SSE connection and confirm the replay resumes after the last event id.
- Confirm the version page renders after `awaiting_approval`.
- Confirm approve and revise still update the campaign status and version count.
